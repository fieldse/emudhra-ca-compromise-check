What happened

On 17 October 2026 a researcher found that eight eMudhra G3 intermediate CAs had private keys anyone can compute. With them, anyone can issue a TLS certificate for any website, or sign malware that Windows treats as coming from a trusted publisher.

Cause
  • A rehearsal step in the key ceremony: At the 30 April 2025 ceremony, eMudhra issued the CA certificates over re-imported key objects instead of the original keys.
  • Which keys: Only the P-384 keys of series B and C, made on Utimaco HSMs, are affected.
  • Two accounts: eMudhra first blamed similar key labels, then said the ceremony script itself chose the re-imported keys.
Downstream impact
  • Forged websites: Anyone can issue a TLS certificate for any website under the six TLS CAs, and every client that still trusts the chain accepts it.
  • Signed malware: The two code-signing keys can make malware look like it comes from a trusted publisher on Windows.
  • Forged certificates already exist: One commenter counted 107,107 certificates logged under six of the keys after disclosure, 106,050 of them proof-of-concept certificates for google[.]com. Nobody has confirmed the count.
What eMudhra has done since
  • Leaving TLS: eMudhra decided on 22 October to leave the global TLS certificate market.
  • Certificates still valid: 25,058 G3 certificates were still valid on 28 October, and eMudhra is moving their subscribers to other roots.
  • Report still owed: eMudhra had not filed its promised root-cause report by 31 October.
  • KPMG review: eMudhra says KPMG is reviewing it, a claim only its own status page makes.

Who is exposed

Browsers on default settings are covered by pushed blocks and root store changes, and anything that carries its own trust store stays exposed until it gets its own update.

Software with its own trust store includes OS bundles, language packages, JDK cacerts, runtimes, Electron apps and container images.

By client

Browsers on default settings
  • Covered. Chrome's CRLSet reached users on 17 October.
  • Mozilla says Firefox's OneCRL block did too, though its NSS 3.131.1 announcement says 19 October.
  • Apple, Windows and Edge pushed their own blocks between 19 and 22 October.
New Firefox ESR 115 profile
Can still trust the chains until OneCRL loads after 20 idle seconds.
Apps with their own CA bundle
  • Need their own update, even on a patched Windows host.
  • Microsoft says software that doesn't reliably check revocation or its disallowed list can still accept the chains if it keeps or restores trust in the removed roots.
macOS command-line tools
Tools that read /etc/ssl/cert.pem, including curl, git, python3, ruby, perl and openssl, skip Apple's block and still accept the chains.
Containers
A container trusts the CA bundle inside its image, so a patched host does not protect it.
Node.js
Bundles a Mozilla snapshot fixed at release time, so only a Node.js upgrade changes it.
JDKs
  • A JDK update fixes only its bundled cacerts.
  • An app's own JKS or PKCS12 truststore needs the roots removed from that file.
Electron apps
  • Electron's advisory gives 42.11.16, 43.8.1, 44.9.1 and 45.0.0-beta.6 as the first releases that block the intermediates in its Chromium networking and Node.js TLS.
  • Each Electron app needs its own release on one of them.
  • Fixed Electron builds still contain the G3 root, so check each app's Electron version to tell fixed from unfixed.

The AAA Certificate Services path

  • A store with AAA Certificate Services and no G3 root can still trust a forged chain. Sectigo cross-signed all eight compromised intermediates under its AAA Certificate Services root, and each cross-sign reuses the same weak key. A forged leaf can chain through those cross-signed copies to AAA, so removing emSign ECC Root CA - G3 alone does not block it.
  • Before the incident Apple and Microsoft still trusted AAA. Mozilla and Chrome had removed it.
  • Fixes that block by public key also catch the cross-signs. Go's crypto/x509 denylist, rustls-webpki 0.103.16 and CPython's ssl block match the compromised keys. So do Chrome's CRLSet and the Windows Disallowed CTL. A fix that only removes the G3 root leaves the AAA path open wherever AAA is still trusted.

How each root program and Sectigo handle AAA and the cross-signs:

Microsoft
  • Removed AAA. Windows dropped it on 26 October, and Edge and WebView2 on 27 October.
  • The 20 October Disallowed CTL block matches the keys, so it covers the cross-signs too.
Mozilla
  • Trusts AAA for email only. NSS and Firefox carry the root without TLS trust.
  • Mozilla left the cross-signs out of OneCRL, saying the root is not in its root store.
Apple
  • Blocks the six TLS cross-signs. They are among the 12 TLS certificates Apple blocks.
  • In /etc/ssl/cert.pem they still verify through AAA, so Apple's interim steps offer removing AAA as well as G3.
Chrome
  • Its store holds no AAA root. Chrome Root Store v41, v42 and v43 do not contain it.
  • Chrome's CRLSet blocks by public key, so it covers the cross-signs anyway.
Sectigo
  • Revoked the cross-signs on 19 October.
  • Its AAA Certificate Services CRL backdates the revocations to 14 May 2025.
  • Clients that skip revocation checks, such as the macOS tools that read /etc/ssl/cert.pem, still accept the chains.

Revocation and CT

  • Common tools could not fetch eMudhra's revocation data until 26 October. eMudhra's firewall refused HTTP CRL and OCSP requests from curl, Wget, Python-urllib and libwww-perl user agents from 28 September 2022 to 10:32 UTC on 26 October 2026. The blocked files include the two CRLs that carry the eight revocations. HTTPS was no fallback, because the certificates name HTTP CRL URLs.
  • Clients that don't enforce CT are more exposed. CT-enforcing clients reject a leaf that was never logged. Non-browser clients such as curl usually don't enforce CT.
  • 106,058 post-disclosure CT certificates chain through the AAA cross-signs, by one count. Nobody has replicated the count.

Chrome blocked the keys within hours of the 17 October disclosure, and Mozilla, Apple and Microsoft removed or blocked emSign ECC Root CA - G3 between 20 and 27 October.

Root programs

Chrome
  • Removed emSign ECC Root CA - G3 in Chrome Root Store v43. Version 42 still has it.
  • Google expected v43 on all devices on the morning of 27 October (Pacific time). No source we read confirms it shipped.
  • The 17 October CRLSet blocks by public key, so it also covers the Sectigo cross-signs.
Mozilla
  • Removed the root in NSS 3.131.1 on 20 October. The release also removes emSign Root CA - C1 and emSign ECC Root CA - C3.
  • Firefox 158.0.1, ESR 153.5.1 and ESR 115.43.1 shipped the same day with the block built in, for users whose settings keep OneCRL from updating.
  • Whether ESR 115.43.1 is fixed is disputed.
Microsoft
  • Removed six emSign G3 roots and AAA Certificate Services.
  • Windows removed them in a 26 October out-of-band update (KB5134133, KB5134137).
  • Edge and WebView2 removed them on 27 October, in PKI Metadata 72.0.0.0.
  • On 20 October the Windows Disallowed CTL had already blocked the eight keys, and Edge CRLSet 2026.10.20 had blocked the TLS keys.
Apple
  • Blocks the 12 TLS certificates and the G3 ECC root. The 12 are the six eMudhra TLS CAs and their six Sectigo cross-signs.
  • The root block started on 23 October.
  • Apple dates the first block to 19 October. The community tracker says 22 October.
  • Command-line tools that read /etc/ssl/cert.pem skip Apple's block.
  • No root program has removed emSign Root CA - G1. Chrome Root Store v43 and NSS master still carry it. Mozilla said on 20 October it was not removing it at that time. Microsoft is evaluating the remaining eMudhra roots. OpenJDK's interim fix deletes the G1 alias anyway.
