Remove AAA Certificate Services with G3

Remove AAA Certificate Services along with emSign ECC Root CA - G3. Removing G3 alone leaves the six Sectigo TLS cross-signs trusted through AAA.

Mozilla advised distributions that cannot block the intermediates to consider removing AAA Certificate Services, emSign Root TLS CA - G3 and emSign ECC Root CA - G3.

Fixes by area

OS trust stores

Fix: update the OS. Most Linux distributions removed emSign ECC Root CA - G3 from their CA package. Windows blocks the eight keys through the Disallowed CTL, and Android received its block through Google Play services on 19 October 2026.

Where the fix falls short

  • Check for AAA Certificate Services as well as G3. Unfixed Debian packages and the Ubuntu 22.04 and 24.04 release builds hold it. Unfixed Red Hat-family packages hold it in the email and code-signing bundles.
  • Check the code-signing bundle on Fedora and CentOS Stream 10. Fedora’s first update and CentOS Stream 10’s current build take G3 out of TLS trust but still trust emSign Root CS CA - G3 for code signing.
  • Match RHEL against the .3 builds. On RHEL only the .3 builds are advisory versions.
  • Fix /etc/ssl/cert.pem on macOS by hand. curl, git, python3, ruby, perl and openssl from macOS or the Command Line Tools trust /etc/ssl/cert.pem and skip Apple’s block and revocation checks. macOS 26.6.2 ships it with both roots, and its /usr/bin/curl completes HTTPS to hosts serving the compromised chains (checked 2026-10-31).
  • Keep the removed roots out on Windows. On 26 October 2026 Windows removed seven certificates, including one Microsoft calls an AAA Certificate Services cross-sign, whose thumbprint is the AAA root’s. Microsoft says software that doesn’t reliably check revocation or its disallowed list can still accept the compromised chains if it keeps or restores trust in the removed roots.
  • Update Windows apps that carry their own CA bundle. The community tracker says they need their own update.

No fix yet

These releases had no fixed package on 2026-10-31:

ReleaseNewest package checked
Debian 11Still trusts the G3 and AAA roots
openSUSE Leap 15.6Still trusts the G3 root
openSUSE Tumbleweed on aarch64Still trusts the G3 root
Amazon Linux 2027 previewNo fixed package

Until a fix ships

  • macOS: Remove the roots from /etc/ssl/cert.pem with Apple’s interim steps, which remove emSign ECC Root CA - G3 and optionally AAA Certificate Services. A macOS update can replace the file, so re-check it after every update. The community tracker reports that 27.2 undid hand edits.
  • Bottlerocket 1.67.0 and earlier: Apply AWS’s settings.pki override. It sets trusted = false for emSign ECC Root CA - G3, C3 and C1 through apiclient apply until the node runs 1.68.0. The override does not list AAA, which is not in the bundle 1.67.0 uses.
  • Disconnected Windows devices: Deliver the updated CTLs another way, because without automatic updates or internet access the CTL Updater cannot fetch them. Microsoft gives 01dd5f6ca45c9d86 as the sequence number of the Disallowed CTL with the eMudhra block.
  • Android devices without the Play services block: Restart first, which triggers the update. Failing that, the community tracker suggests disabling emSign ECC Root CA - G3 and AAA Certificate Services under Settings, Trusted credentials, System.

Java

Fix: upgrade each JDK to a build that removes both G3 and AAA Certificate Services, then restart every running JVM. A JVM keeps the old store until it restarts.

Where the fix falls short

  • Check every JDK on the machine. Each installation has its own cacerts.
  • Grep for fingerprints and owner names. The same G3 root sits under four alias styles. keytool -list prints SHA-256 fingerprints by default and -v adds the owner, so grep for both.
  • Rebuild Debian and Ubuntu’s Java keystore after updating ca-certificates. The package update doesn’t refresh /etc/ssl/certs/java/cacerts. Run these as root to rebuild it:
    rm -f /etc/ssl/certs/java/cacerts
update-ca-certificates --fresh
  • Clean application truststores by hand. They keep the roots until you remove them. Run the keytool -delete from the stopgap below with -keystore and the file’s password.
  • Update Homebrew and FreeBSD OpenJDK on their own. They carry their own store and need their own update.
  • Don’t go by the version number. The .0.2 builds from OpenJDK, Oracle and SapMachine still hold G3 and AAA, but Temurin 27.0.1.0.2+1 is fixed. Azul’s fixed Zulu 21 subscriber build reports JDK 21.0.12.1, and the free 21.0.13 build still holds all four roots.
  • Expect one BAD ROOT line on fixed Temurin. It keeps G1 on purpose, so OpenJDK’s CheckCerts prints BAD ROOT: CN=emSign Root CA - G1,… there.
  • Expect emSign C1 and C3 in fixed Corretto. A reply on Corretto’s issue tracker says they don’t chain to the compromised intermediates.

No fix yet

These builds had no fix on 2026-10-31:

BuildStatus
Temurin 8 and 11Still trusts G3
eclipse-temurin:27-jreStill trusts G3
The free Azul Zulu 21 build (disputed)Still holds G3 and AAA
Microsoft Build of OpenJDK 21 and 25Still holds G3 and AAA
IBM Semeru 8 and 11IBM names no fix
Oracle GraalVMNo fixed build was found

Until a fix ships

  • Delete G3 and AAA from each cacerts under the vendor’s own alias. OpenJDK’s stopgap:
    1. Back up the file.
    2. Run keytool -delete -cacerts -alias "emsigneccrootcag3 [jdk]" for each of the four [jdk] aliases.
    3. Ignore "does not exist" errors.
    4. Restart running JVMs.
  • Find the alias first on Temurin, Microsoft and Corretto. The [jdk] alias names miss Temurin, Microsoft and Corretto’s second copy. Run the fingerprint check with grep -B1 first to print each matching entry’s alias.
  • On JDK 8, point keytool at the file. Use -keystore "$JAVA_HOME/jre/lib/security/cacerts" in place of -cacerts.
  • Turn on revocation checking as a last resort. For TLS clients, OpenJDK suggests adding -Dcom.sun.net.ssl.checkRevocation=true -Dcom.sun.security.enableCRLDP=true to the java command line. For signed JARs on JDK 17 and later, it suggests jarsigner -verify -revcheck -strict on each JAR.

Python

Fix: upgrade pip to 26.2.2 and certifi to 2026.10.19 in every venv. Python 3.15.2, 3.14.10, 3.13.18, 3.12.16 and 3.11.18 add an ssl block on the compromised keys that also catches the Sectigo cross-signs.

Where the fix falls short

  • Upgrade pip in every venv. Each venv keeps its own pip, so upgrading the interpreter leaves existing venvs on their old pip. A venv has a pyvenv.cfg at its root, so search for that file to find them all.
  • Treat venvs made by Python 3.11 and 3.12 as affected. Current releases bundle pip 24.0 and 25.0.1, both holding G3 and the AAA root. A reply on the PSF thread says security releases will not upgrade them.
  • Don’t count on a fixed OS store to fix pip. pip always trusts its vendored certifi. From pip 24.2 on Python 3.10 and later it also trusts the OS store.
  • Skip certifi 2026.10.18. GHSA-6q48-6c7w-9gw2 names it as the first patched release, and the PSF recommends 2026.10.19. 2026.10.18 removed every emSign root, including the unaffected G1, C1 and C3, and users reported broken connections. 2026.10.19 restores those three and still leaves out G3.
  • Check old certifi pins for AAA. The advisory range starts at 2019.03.09 and covers the G3 root only. Every certifi up to 2025.1.31, including 2018.11.29, holds the AAA root.
  • Fix certifi for requests and HTTPX, and the OS store for truststore. requests and HTTPX use certifi, and truststore uses the OS store.
  • Run uv python upgrade for uv-managed interpreters. After uv 0.13.5, it replaces the managed 3.11 and newer interpreters.
  • Upgrade standalone Pixi. It needs 0.82.1.
  • Update conda’s CA packages in every environment. Updating base leaves the others alone.

No fix yet

  • Python 3.10 and older are end of life and get no fix.
  • Anaconda main has no fixed CA packages for osx-64, linux-ppc64le or linux-s390x.

Until a fix ships

  • Bootstrap uv through the OS verifier: --system-certs, UV_SYSTEM_CERTS=true or system-certs = true in uv.toml make uv verify with the operating system instead of its bundled roots, for example UV_SYSTEM_CERTS=true uv self update. Fix the OS store first.
  • Point uv at a fixed bundle: SSL_CERT_FILE or SSL_CERT_DIR replaces uv’s default certificate source entirely, so a fixed file such as the cacert.pem from certifi 2026.10.19 takes over.
  • Point requests at a fixed bundle: REQUESTS_CA_BUNDLE or CURL_CA_BUNDLE makes requests use that file instead of certifi. These settings do not help pip, which keeps its vendored roots and only adds the extra CAs.

JavaScript runtimes

Fix: upgrade each runtime to its fixed release. Node.js’s fixed releases move to NSS 3.131.1, which drops G3, and reject chains with blocked public keys.

Where the fix falls short

  • Don’t rely on extra CA settings. NODE_EXTRA_CA_CERTS, --use-system-ca and NODE_USE_SYSTEM_CA=1 add certificates to the bundled roots. Node does not apply the system’s distrust settings.
  • Upgrade Deno 2.9.7. It also holds the AAA root.
  • Confirm the fix by grepping the binary. Node stores its roots as PEM text, so the first base64 line of the G3 root appears in an affected binary and not in a fixed one. Bun and Deno store DER, so grep their binaries for the subject string emSign ECC Root CA - G3.
  • Grep node_modules in each project. Electron’s is the only npm advisory for this incident between 2026-10-17 and 2026-10-31, and no advisory names a package with a vendored bundle. An advisory search cannot prove that no package vendors the root.
    # Lists each file under node_modules that holds the G3 root. Prints nothing if none does
grep -rlF 'MIICTjCCAdOgAwIBAgIKPPYHqWhwDtqLhDAKBggqhkjOPQQDAzBrMQswCQYDVQQG' node_modules 2>/dev/null

No fix yet

  • Node.js 20 has been end of life since 2026-04-30. Its last release, 20.20.2, still bundles G3.

Until a fix ships

  • Node.js on Linux: Run it with --use-openssl-ca once the distribution store is fixed. The flag replaces the bundled roots with OpenSSL’s default store, which most Linux distributions maintain. This was not tested against a fixed store.
  • Deno: Run it with DENO_TLS_CA_STORE=system once the OS store is fixed. The variable picks the system store, the bundled Mozilla roots or both, in order, and defaults to the bundled roots. Upgrade to 2.9.8 anyway, because it was not traced which 2.9.7 code path loads the AAA root.

Other languages

Fix: upgrade to a release that blocks the eight compromised public keys. Go 1.26.10 and 1.27.3, rustls-webpki 0.103.16, and composer/ca-bundle 1.6.0 and 1.4.16 match those keys, which Sectigo’s cross-signs share. Composer 2.11.0 and 2.2.31 reject the intermediates even when the system store trusts their roots.

Where the fix falls short

  • Pin the Go fallback roots by hand. golang.org/x/crypto/x509roots/fallback embeds its own roots and has no entry in the Go vulnerability database, so govulncheck misses an old pin. Pin v0.0.0-20261020153306-9f2b28d4331a or later and rebuild.
  • Check both webpki-roots lines in the Rust lock file. webpki-roots 0.26.11 holds no roots and is safe only when the lock file also resolves the 1.x crate to 1.0.10 or later.
  • Fix the OS store for PHP, RubyGems, Bundler, Erlang/OTP public_key, .NET and rustls-native-certs. They follow the OS store. rustls-native-certs ignores OS distrust settings, and .NET on Linux ignores the Disallowed store, so remove the root from the store itself.
  • Rebuild Dart and Flutter apps for Android and Windows. Those apps ignore OS blocklists. Rebuild them with Dart 3.13.7 or Flutter 3.47.8.
  • Take AAA out too where a package removes only G3. webpki-roots, excon, castore, Hex certifi, Mozilla::CA and curl’s cacert.pem remove the G3 root. That leaves the cross-signs unblocked wherever the AAA root is trusted.
  • Upgrade old pins that hold AAA. The releases in the table below bundle the AAA root as well as G3, and so does everything before them. Upgrade them to the first release after the incident.

No fix yet

  • RUSTSEC-2026-0381 patches nothing else below webpki-roots 1.0.10, so 0.25.x and older have no fix.
  • httpclient 2.9.0, the latest release, loads its own bundle by default and has no fix. That bundle is Mozilla data from 2015 with the AAA root and no G3 root, so a check for G3 alone passes it.

Until a fix ships

  • SSL_CERT_FILE: Point Go, curl, .NET on Linux and rustls-native-certs at curl’s cacert-2026-10-20.pem, which holds neither the G3 root nor the AAA root. All four read SSL_CERT_FILE. The curl tool reads it and CURL_CA_BUNDLE only when it uses no native store, and a Schannel build on Windows ignores both. From Go 1.27, setting it on macOS or Windows turns off Go’s platform verifier.
  • .NET on Linux: Remove the roots from the OpenSSL bundle. .NET ignores the Disallowed store when it builds chains on Linux.
  • Go containers: Keep a fixed CA bundle in the image and leave GODEBUG=x509usefallbackroots=1 unset. Go then uses the system roots and never the embedded fallback bundle.
  • Perl: Give it a fixed, usable system store. IO::Socket::SSL clients such as LWP and HTTP::Tiny load Mozilla::CA only when no usable system store is found.

Browsers and apps

Fix: update each app to its fixed release. Browsers on default settings block the intermediates without an update, apart from a Firefox ESR 115 startup gap.

Where the fix falls short

  • Don’t go by CVE-2026-113470 for Firefox ESR 115. It still lists 115.43.1 as fixed. ESR 115 has no released fix for new profiles. It loads OneCRL only after 20 seconds without input, and the fix is in an unreleased 115.45.0.
  • Check Firefox forks that drop OneCRL. A fork that drops OneCRL, such as GNU IceCat built from ESR 153.5.1, still trusted the intermediates.
  • Update every Electron app. There is no app-side workaround.
  • Don’t judge Electron by a root grep. The fix blocks the intermediates and leaves the G3 root in place. Grepping the binary for the root’s PEM line shows the bundled Node.js store, and it matches on fixed releases too.
  • Upgrade VS Code desktop to 1.144.0. 1.143.1 changed only the remote server’s Node.js.
  • Upgrade Docker Desktop to 4.96.3. It is the first release whose notes drop the partial-fix warning. The community tracker lists 4.96.2.
  • Upgrade to certbot 5.9.0 and LibreOffice 26.8.2. Both shipped fixes that the community tracker still lists as pending.
  • Upgrade JBR to b635.79. b635.78 blocks all 16 certificates but its cacerts keeps the G3 and AAA roots. b635.79 removes them.
  • Check Godot 3 for AAA. It bundles AAA as well as the G3 root.

No fix yet

ProjectStatus

PodmanNo stable release since 12 October
GodotFix on master only

Until a fix ships

  • Firefox ESR 115: Leave a new profile idle for 20 seconds before first use, so it loads OneCRL. Once OneCRL loaded, the tracker’s test page showed none of the 14 chains trusted.

Container images

Fix: check each image and rebuild it. Patching the host does not fix its containers, because each container trusts the bundle inside its image.

Where the fix falls short

  • Check the built image on Debian and Ubuntu bases. The base images carry no bundle. Whichever later layer installs ca-certificates sets what the image trusts.
  • Read images with no shell without running them. Copy the bundle or the dpkg status entry out with create and cp.
  • Upgrade ca-certificates in Rocky Linux and Amazon Linux images. The current rockylinux:8, :9 and :10 images still ship unfixed builds. So does amazonlinux:2023. The upgrade for each is under Until a fix ships.
  • Move to Alpine 3.24.3 and the certbot v5.9.0 image. Both are fixed. Alpine 3.24.2 and certbot v5.8.0 still hold the G3 root.

Until a fix ships

  • Base images that lag: Upgrade ca-certificates in the image build. On rockylinux:8, :9 and :10, dnf upgrade ca-certificates installs the fixed builds. On amazonlinux:2023, add --releasever=latest to the update, or it keeps the unfixed build.
  • Distroless images: Move them to Debian 13. static-debian13 ships the fixed ca-certificates 20250419+deb13u1. The Debian 12 images had no fix on 2026-10-31.
  • podman machine VM: Update the VM’s own ca-certificates. The VM keeps a store separate from the host, and the community tracker gives Fedora 2026.2.92_v9.0.319 as fixed.
